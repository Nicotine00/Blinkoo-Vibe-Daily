# 任务证据协议

> 临时功能名。先把协议做对，再考虑品牌命名。

## 目标

这套协议只解决一件事：

**禁止 Agent 用“看起来应该对”冒充“已经验证对”。**

常见错误不是完全胡说，而是证据只走到一半，Agent 自己补完剩下的一半：

- 看见 CSS 坐标正确，就宣布视觉位置正确
- 看见代码逻辑合理，就宣布功能已经正常
- 看见单元测试通过，就宣布整个产品可用
- 看见旧数据，就宣布当前数据仍然成立
- 看见文件写入请求成功，就宣布远端仓库内容已经正确
- 看见用户没有反对，就宣布用户已经认可
- 没有真实运行，只凭“应该可以”写成“已验证”

本协议要求 Agent 从接任务开始就规划证据，执行时收集证据，交付时只说证据能够支持到的结论。

---

## 一、核心铁律

### 1. 每一个“通过”都必须绑定证据

如果无法回答下面两个问题，就不能写“通过”：

1. 用什么验证的？
2. 这个验证方式真的能证明这一项吗？

没有证据时，只能写：

- 未验证
- 待验证
- 等待用户确认
- 当前只有静态推断
- 当前环境无法验证

### 2. 验证方式必须匹配需求属性

不能拿低维证据证明高维结论。

例如：

- 坐标值不能证明视觉正确
- 静态代码检查不能证明运行正常
- 单元测试不能证明交互手感良好
- 模型记忆不能证明实时数据正确
- 文件存在不能证明文件内容正确
- 编译通过不能证明业务目标达成

### 3. 不具备验证能力时，不准补全结论

Agent 可以完成自己能完成的部分，但必须把验证边界写清楚。

无法看到最终渲染画面，就不能替用户确认视觉效果。

无法访问真实生产数据，就不能替用户确认生产数据正确。

无法真实操作硬件，就不能替用户确认设备行为正常。

### 4. 不允许把推测改写成事实

下面这些表达都属于未验证：

- 应该可以
- 理论上没问题
- 看起来没问题
- 按代码判断已经修好
- 大概率正常
- 预计不会出错

它们可以作为分析，但不能进入“已完成 / 已通过 / 已确认”。

---

## 二、接到任务后的第一步：拆需求，不急着执行

Agent 先把用户要求拆成可独立判断的验收项。

内部至少形成这张表：

| 字段 | 含义 |
|---|---|
| requirement | 用户真正要求什么 |
| property | 这项要求属于什么属性 |
| ambiguity | 有没有会影响结果的歧义 |
| verification | 正确的验证方式 |
| evidence | 需要拿到什么证据 |
| capability | 当前 Agent 能不能自己验证 |
| pass_condition | 满足什么条件才算通过 |

简单任务可以在内部完成，不必把表完整展示给用户。

复杂任务、关键任务、存在明显歧义的任务，先把关键验收条件告诉用户。

---

## 三、什么时候必须先问用户

不是所有模糊都要问。只有歧义会改变结果或验收标准时才问。

必须澄清的情况：

- “优化一下”“更高级”“更舒服”“像某产品”这类词会直接决定结果
- 用户指定了结果，却没给必要目标值、范围、样例或数据源
- 存在两个以上差异明显的合理实现
- 操作不可逆或有明显风险
- 用户要求“准确”“一致”“完全一样”，但没有定义比较基准
- 主观审美会决定最终通过与否

可以不问的情况：

- 歧义不影响最终验收
- 项目已有明确规范
- 用户已给样例或基准
- 可以安全采用行业默认值，并明确记录假设

原则：

**只问会改变结果的问题，不把协议变成审讯。**

---

## 四、属性分类与证据边界

### A. 事实 / 数据属性

包括：

- 数值
- 排名
- 日期
-价格
- 用户量
- 增长率
-政策状态
- API 返回结果
- 外部产品当前状态

最低要求：

- 有真实来源
- 有时间范围
- 有统计口径或适用范围
- 必要时保留原始数据或计算过程

禁止：

- 用模型记忆代替当前数据
- 没查来源就写“官方数据显示”
- 用旧数据证明当前状态
- 不同统计口径直接比较

如果用户说“帮我查数据”，最终交付必须能指出数据来自哪里。

### B. 代码 / 静态结构属性

包括：

- 文件是否存在
- 函数是否实现
- 类型是否正确
- 依赖是否引用
- 配置是否写入
- 代码结构是否符合规则

可用证据：

- 实际读取文件
- Git diff
- 静态分析
- 类型检查
- lint
- 编译结果

边界：

静态证据只能证明静态属性，不能自动升级为“功能已经能用”。

### C. 运行 / 功能属性

包括：

- 页面能否打开
- 登录是否成功
- 保存是否生效
- API 是否通
- 命令是否执行成功
- 游戏功能是否触发

最低要求：

必须实际运行、调用或执行测试。

只看代码不能判定运行功能通过。

如果当前环境无法运行：

状态必须是“实现完成，运行未验证”。

### D. 视觉 / 布局属性

包括：

- 居中
- 对齐
- 遮挡
- 尺寸观感
- 颜色
- 像素效果
- 响应式布局
- 游戏场景显示

最低要求：

必须检查真实渲染结果、截图、画面或可视化输出。

禁止：

- 根据 x/y 坐标宣布“视觉位置正确”
- 根据 CSS 属性宣布“页面显示正常”
- 根据节点尺寸宣布“没有遮挡”

如果 Agent 没有视觉检查能力：

必须交给用户做视觉验收。

### E. 交互 / 使用体验属性

包括：

- 拖拽是否顺手
- 点击流程是否自然
- 操作是否容易理解
- 游戏手感
- 快捷键体验
- 动画节奏

最低要求：

真实交互测试。

如果 Agent 有计算机操作能力，可以执行客观流程；涉及“舒服、顺手、自然”等主观感受时，最终仍由用户确认。

### F. 性能属性

包括：

- 更快
- 更省内存
- 延迟降低
- 加载速度提高
- 包体积减少

最低要求：

真实测量，并保留对比基线。

禁止：

- “代码更简洁，所以性能更好”
- “换了算法，所以速度提升”
- 没有前后数据就写“性能优化完成”

### G. 文件 / 仓库 / 同步属性

包括：

- 文件已上传
- 提交已产生
- GitHub 已同步
- 分支正确
- 远端内容正确

最低要求：

写入后必须重新读取目标状态。

例如 GitHub 操作：

1. 执行写入
2. 获取提交 SHA
3. 重新读取远端文件或目录
4. 确认内容和路径
5. 才能宣布同步成功

“API 返回成功”只能证明请求成功，不能单独证明最终内容符合要求。

### H. 主观质量属性

包括：

- 好看
- 高级
- 有质感
- 符合用户审美
- 像某种风格
- 玩起来有趣

Agent 可以辅助分析，但最终通过权属于用户，除非用户提前给出了可客观执行的评分标准。

状态通常应为：

“客观条件已满足，等待用户主观验收”。

### I. 安全 / 风险属性

包括：

- 没有泄露密钥
- 没有破坏旧数据
- 权限正确
- 输入不会造成危险行为

证据可以来自：

- 配置检查
- secret scan
- 权限检查
- 回归测试
- 备份 / Git 状态

禁止绝对化：

除非验证范围足够，否则不要写“绝对安全”“不存在任何风险”。

---

## 五、证据匹配原则

证据不是越多越好，关键是与属性匹配。

同一个任务可以同时需要多种证据。

例如：

用户要求“把上传按钮移动到右上角，并保证手机上不遮挡内容”。

这句话至少包含：

1. 文件修改属性
2. 桌面视觉属性
3. 移动端视觉属性

正确验证不能只有：

“CSS 已改，坐标为 right: 16px。”

必须继续检查真实桌面和移动端渲染。

如果 Agent只能修改代码，没有浏览器或截图能力：

可以确认“CSS 已修改”。

不能确认“位置正确、手机无挡住内容”。

---

## 六、执行中的规则

### 1. 边做边验证

不要全部写完以后再想怎么证明。

能立即验证的步骤，完成后立即验证。

### 2. 保存原始证据

重要任务尽量保留：

- 命令输出
- 测试结果
- 数据源
- 截图
- Git diff
- commit SHA
- API 返回
- 实际文件内容

### 3. 失败不能被吞掉

测试失败、工具失败、权限失败、访问失败必须保留。

不允许因为后续步骤成功，就省略前面的失败。

### 4. 替代验证必须说明降级

如果原计划无法执行，只能用弱证据替代，要明确写：

“原计划验证 A 无法执行，目前只有 B 证据，因此此项仍未完全验证。”

---

## 七、任务结束时的状态体系

单项状态只允许使用：

- PASS：已有匹配证据，达到通过条件
- PARTIAL：部分达到，仍缺一部分
- NEEDS_USER：客观部分已完成，需要用户确认
- NOT_VERIFIED：已实现或已修改，但没有完成验证
- BLOCKED：因权限、环境、依赖等无法继续
- FAIL：验证明确失败

整个任务的最终状态由单项状态推导。

只有全部必要验收项都是 PASS，且没有必须由用户确认的项目时，才能写：

**已验证完成**

存在 NEEDS_USER：

**实现完成，等待用户验收**

存在 NOT_VERIFIED：

**实现完成，验证未完成**

存在 FAIL：

**验收失败**

禁止为了让汇报好看，把 PARTIAL、NEEDS_USER、NOT_VERIFIED 改写成“基本完成”或“100%完成”。

---

## 八、交付格式

简单任务不要输出长报告，只写关键证据和未验证项。

推荐：

```
结果：
- 数据文件已更新：PASS
  证据：重新读取远端文件，目标字段已存在
- 自动测试：PASS
  证据：38/38 tests passed
- 移动端布局：NOT_VERIFIED
  原因：当前没有真实移动端渲染检查

最终状态：实现完成，移动端视觉待验收
```

复杂任务可以使用：

```
[验收项]
要求：
属性：
验证方式：
证据：
状态：

[边界]
当前仍无法确认：

[最终状态]
```

## 九、典型反例

### 反例 1：靠坐标验视觉

错误：

“按钮坐标已经改到目标位置，视觉验收通过。”

正确：

“坐标已按要求修改。尚未检查最终渲染画面，视觉位置待确认。”

### 反例 2：靠代码验功能

错误：

“登录逻辑已经修复，可以正常登录。”

正确：

“登录逻辑已修改，类型检查通过。尚未执行真实登录流程，因此运行状态未验证。”

### 反例 3：靠记忆报数据

错误：

“该产品目前有 500 万用户。”

正确：

“当前没有查询到可核实的数据源，因此不能确认最新用户量。”

### 反例 4：工具返回成功就当文件正确

错误：

“GitHub 上传成功，Skill 已部署。”

正确：

“写入请求成功，并重新读取远端路径确认 SKILL.md 内容存在且与目标内容一致，部署通过。”

## 十、与其他项目规则的关系

本协议优先约束“怎么判断完成”。

项目自身的 AGENTS.md、开发手册、设计规范负责定义“应该做成什么”。

两者组合：

```
项目规范
负责定义目标
↓
本协议
负责把目标拆成可验证属性
↓
执行
↓
按属性匹配证据
↓
能证明的通过
不能证明的明确交给用户
```

如果项目规则和本协议冲突：

- 项目业务目标听项目规则
- “是否已经验证”听本协议
- 任何规则都不能允许无证据宣布通过

## 十一、Agent 自检

在发送最终结果前，逐条检查：

1. 我有没有把用户需求拆成独立验收项？
2. 有没有影响结果的歧义被我偷偷猜过去？
3. 每个“通过”后面有没有真实证据？
4. 证据类型和要求属性是否匹配？
5. 有没有拿静态检查证明运行结果？
6. 有没有拿坐标、CSS、代码结构证明视觉结果？
7. 有没有拿模型记忆证明实时数据？
8. 有没有声称执行了实际上没执行的测试？
9. 有没有我自己无法判断，却替用户做了主观确认的部分？
10. 如果用户问“你凭什么说完成了”，我能不能逐项回答？

任意一项答案有问题，降低状态，不准宣布全部完成。
