# 瞭望台：项目间互通协议

一句话：把 N 个各自为政的项目，接进一张互通网，让项目与项目之间按需互相供给，而不是互相失明。

注意，瞭望台解决的是项目之间的分工问题，不是 AI 的记忆问题。AI 记性不好是另一回事；这里要治的是，你的项目们彼此不认识、不读写对方的消息。

## 三种互通（先分清你要的是哪种）

| 互通类型 | 是什么 | 通用示例 |
|---|---|---|
| 规格互通 | 一方声明自己能供给什么规格，另一方声明自己需要什么规格，两方按同一口径交接 | 素材工具按游戏项目的素材规格产出；音频项目按视频项目的时间轴规格交付 |
| 数据互通 | 多端共享同一份数据源，任何一端都不得另起一套 | 同一产品的 Web 版与小程序版读写同一数据库；内容库与分发端共用同一份稿件 |
| 情报互通 | 一方实时掌握其他项目近期做了什么 | 内容策划每次开工自动拿到全项目进展；团队负责人一眼俯视全局 |

同一条链路可以同时是多种互通。先列出每个项目的产出物、消费物、依赖谁，矩阵自然浮现。

## 原理（30 秒理解）

- 每个项目一个 `<项目名>-status.md`，是它对外广播的台子
- 一张 `关联索引.md` 互通地图，写清谁该读谁、谁该供给谁
- 一段全局规则，让每个项目会话开工先看地图、干完写回广播台
- 本 skill 负责把用户口述的项目清单变成这一整套，并持续体检

## 一、Onboarding（用户第一次用，必走流程）

原则：不追着用户问细节，先问一个最小问题，剩下的 AI 自己读、用户只管确认。

1. 只问一个问题：把项目路径列给我（一行一个，一次给全或逐个补充）
2. 逐个读项目目录，自己搞清楚每个项目是干嘛的：项目根 AGENTS.md、README、目录结构，从中读定位、产出物、涉及的外部接口。只读与互通有关的信息，不碰代码细节和密钥
3. 把读到的整理成项目清单，交用户确认两样：每个项目的确认名称（对外沟通口径，跟用户平时称呼一致）和一句话定位
4. 基于已读到的内容主动梳理互通点候选，逐条列给用户确认：
   - 疑似规格互通（产物有上下游关系的项目：工具产出被另一项目消费）
   - 疑似数据互通（同一产品的多个端点，或共用同一份数据/资料的两处）
   - 疑似情报互通（内容型/管理型项目需要全项目近期动态）
5. 若用户全部否认候选，再问开放问题：你希望瞭望塔在这些项目之间做什么
6. 确认完成后，按结果自动产出五样：

- 每项目一个 `<项目名>-status.md`（套模板）
- `<关联索引.md>` 互通矩阵（按确认结果写清每条边）
- 一段全局规则（复制到用户 AI 客户端配置，见下方）
- 每个项目根目录的 AGENTS.md 追加一行维护约定
- 一份汇报，告诉用户每个项目下次会话会自动开始维护

全局规则原文（发布时写进用户配置）：

```markdown
## 跨项目互通（强制）
1. 对话开始：列出状态目录下所有 *-status.md，先读关联索引，再逐文件读
2. 汇报：当前项目与其他项目的互通边（本项目等着谁、谁等着本项目）、每个项目当前任务与最近进展
3. 每完成关键任务：更新本项目的状态文件；若成果涉及馈送其他项目（规格/数据/情报），显式标注供给对象
4. 未进过的项目：写待该会话更新，不编造
```

## 二、状态文件：项目的对外广播台

模板基础四段（当前任务 / 最近进展 / 阻塞 / 下一步），按项目互通需求追加这些段：

- 对外接口，本项目能供给其他项目什么（一份规格、一套数据、一批素材），列表写清
- 消费接口，本项目依赖其他项目供给什么，缺了哪样就堵在哪
- 共享数据源，本项目和谁共用同一份数据，读写约定是什么

更新进展时，凡是馈送其他项目的东西，条目里显式写供给对象，方便对方会话在矩阵里一眼找到自己。

## 三、关联索引：互通矩阵

`关联索引.md` 一张表三列：当前项目 / 应读取的项目 / 互通说明（规格、数据、情报选填并注明）。
任何会话开工先读矩阵，只处理与本项目有关的边，不做全仓广播。

## 四、运行时汇报

1. 列出 `*-status.md`（跳过 README、_TEMPLATE、台账、脚本等系统文件）
2. 先读关联索引，按矩阵汇报当前项目三条边：
   - 谁在等本项目供给，本项目交了吗
   - 本项目在等谁供给，对方走到哪一步了
   - 共享数据源有没有双轨迹象
3. 再逐项目报 当前任务 + 最近进展，打活跃标记
4. 结尾给健康摘要：`N 个项目：X 活跃 / Y 停滞 / Z 占位`

## 五、健康检查

活跃度标记（看状态文件最后修改时间）：

- ✦ 活跃，≤7 天有更新
- ⚪ 停滞，8-30 天未更新
- 🪦 失联，>30 天未更新，建议与用户确认是否退出互通网
- 🧩 占位，内容仍含待该会话更新，机制没被那个项目激活

互通侧重点查三件事：共享数据源有没有出现双轨、规格有没有变更却没人通知消费方、联盟链路有没有哪条断着。

## 六、避坑守则（每条都是真实踩过的坑）

1. 不编造：没进过的项目只写待该会话更新，进展只来自状态文件和用户口述
2. 单真相源：多系统部署副本一律从主源同步，副本上禁止直接改
3. 命名对齐：状态文件名用用户口述的项目全名，不用目录缩写（目录名和项目名不一致时以用户核对外口径为准）
4. 汇报只读状态文件：台账、地图生成物、安装脚本等系统文件不进汇报上下文
5. 双轨必冲突：项目内部已有的日志或记忆系统是运行记录，状态文件是唯一对外口径
6. 规格变更必通知：规格对谁生效，变更就写进进展并点名消费方，防止对方按旧规格干活

## 七、背景与动机（示例已脱敏）

- 起因：多个项目各自为政。素材工具不知道该按什么规格出图，只能反复问下游；同一产品的两个端版本数据各写各的，哪天对不上账才发现；内容策划想拿全项目近期动态做选题，得一个个会话打开问
- 解法：一个广播台（状态文件）+ 一张互通地图（关联索引）+ 一段全局规则，把项目从孤岛变成节点
- 验证：另一套独立的 AI 系统进场后，自动遵守这套约定，还自动在地图上补上自己的节点。协议一旦标准化，任何 agent 都能接入
- 教训：项目间互通的拦路虎不是技术，是口径。统一了对外接口和单一数据源，剩下的事只是复制粘贴约定

## 维护清单（改了本 skill 之后）

- 同步部署副本：运行 `_install_skills.py`（或手动把 SKILL.md 覆盖到每个部署目录）
- 改完确认 README.md 与 SKILL.md 一致
- 涉及互通规则本身的变化，同步检查用户环境中已生成的关联索引是否符合新规则
