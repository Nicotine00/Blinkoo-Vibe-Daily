# 克制 Skill

让 Agent 少猜一步，多拿一步证据。

克制不是语气变保守，也不是每次都说“建议你再测试一下”。

它要求 Agent 从接任务时就先想清楚：

用户到底要求了几件事？
每一条要求来自哪里？
有没有自己偷偷补出的数字、阈值、时间或业务规则？
每件事属于什么属性？
什么证据才有资格证明它？
哪些东西自己能验？
哪些东西必须交给用户验？

复杂任务开工前，Agent 会先给出一个简短的“任务理解 + 验收计划”。用户可以在它写代码之前先确认理解有没有偏。

执行过程中，Agent 必须边做边验证。交付时再把每一项结果对回最初的要求，并说明实际做了什么验证、看到了什么、这些证据能证明什么、还不能证明什么。

## 它主要防什么

- 没看实际画面，只看坐标就说 UI 位置正确
- 没跑程序，只看代码就说功能已经修好
- 没查数据源，就给出一个看起来合理的数字
- 单测通过，就说整个产品 100% 没问题
- GitHub 写入成功，就默认远端文件内容完全正确
- Agent 没能力判断主观体验，却替用户宣布验收通过
- 语气很克制，但实际上没有给出任何验证证据
- 用户只说“多一点”“一周以上”，Agent 却自己补成“+2”“第 7 天开始”
- 拆需求时漏掉用户原始要求，或执行中悄悄多做了未授权规则

## 核心原则

**Agent 只能说到证据能够证明的位置。**

代码证据证明代码。
运行证据证明运行。
视觉证据证明视觉。
数据源证明数据。
用户确认负责主观判断。

低一级的证据不能自动升级成高一级结论。

同样，需求里没有定义的产品规则也不能由 Agent 静默补齐。凡是会改变用户可见行为、奖励、扣费、时间、权限、范围或数据结果的规则，都必须能追溯到用户要求、项目权威规则或已核实来源。否则先问。

## 使用方式

把 `SKILL.md` 放进支持 Skills 的 Agent 工具里，在开发、调试、数据查询、文件修改、UI 调整、GitHub 操作、自动化任务中加载。

简单小任务可以内部拆解。

遇到多要求、视觉、数据、外部平台、风险操作、模糊需求或主观验收时，必须在正式执行前先给用户展示简短的“任务理解 + 验收计划”。复杂任务还要逐项覆盖用户原始需求，发现规则空白时先确认，禁止一边开发一边替用户补产品规则。
